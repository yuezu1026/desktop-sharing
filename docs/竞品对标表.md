> **背景**：`[D12-1]`（`账号与管理系统设计` §7）拍定「**个人版设备数 = 免费版 = 100 台**，且**不作付费权益**」，
> 当时留了一个**未闭合的依赖**：**若对手付费档设备数显著高于 100，我方付费档会在此项显劣**（原登记 §9 #20）。
> 🔴 **本轮用 §2.1 / §3.1 已有抓取数据即可判定 —— 结论是「显劣」**：

| 档位 | ToDesk 设备数 | 价格 | 我方对应档 | 判定 |
|---|---|---|---|---|
| 免费版 | **100 台** | ¥0 | 免费版 **100 台** | ⚪ **同档** |
| **专业版** | 🔴 **150 台** | **¥158/年（¥13.2/月）** | 🔴 个人版 **100 台** | 🔴 **我方显劣（同价更少）** |
| 游戏版 / 设计版 | **200 台** | ¥298/年 | —（我方无此档） | — |
| 性能版 | **300 台** | ¥638/年 | — | — |

**结论与建议**

1. 🔴 **事实层面：「设备数」这一项我方付费档确实显劣**（同价 ¥158/年：对手 **150 台** vs 我方 **100 台**）。
2. ✅ **不变的部分**：**「设备数不作付费点」的判断仍成立** —— 对手给得多也**不构成付费理由**（用户不会为 50 台多付钱），且它**几乎无边际成本**（不连就不花中继）。
3. ⚠️ **但权益对比表的措辞必须改**（`商业化与计费设计` §13.3 原有约束只解决了「别把 100 台写成付费权益」，**没有解决「同价位比对手少 50 台」**）：
   - ❌ **不得回避该行**（用户会自己去 ToDesk 页面看到 150 台 ⇒ **被截图打脸**）；
   - ✅ **必须**并列写出「ToDesk 专业版 150 台 / 我方 100 台」，**同时**在同一屏放进我方两条**真优势行**（**手机被控免费** · **直连不限时长**）+ 一条**同档行**（免费中继额度）；
   - ✅ 对外话术：「**100 台对个人用户足够**（对手免费版也是 100 台）；我们把差异做在**不额外收钱的手机被控**与**可验证的直连不限时长**上」。
4. ❓ **三条可选路线（`[待用户拍板]`，本轮不擅自改数）**：
   - **A 维持现状**（免费 100 / 付费 100）：与 D12-1 一致，靠其他行取胜；**代价** = 对比表需正面承认该项落后；
   - **B 两档都提到 150 台**：边际成本 ≈ 0，**直接消掉对比劣势**，且为 D8 主主张**新增第三条可验证证据**；**代价** = 需**修订 D12-1**，且要回答「为何是 150 而不是 100」；
   - **C 付费档 150 / 免费档 100**：与「设备数不作付费点」**直接冲突**，**不推荐**。

> 🔴 **拍板前**：对外材料**不得出现任何设备数对比措辞**；本项已进 `需求规划评审意见.md` §10 待确认总台账。

## 3. 免费版限制对比（消费级真正的胜负手）

### 3.1 ToDesk 免费版（级别 A，逐条抓取）

| 维度 | 免费版实际限制 |
|---|---|
| **时长 / 次数** | 普通免费节点 **不限时不限次** |
| **带宽上限** | **4 Mbps**（独享传输带宽上限） |
| **PC 帧率** | 最高 **30 FPS** |
| **分辨率** | 最高 **1080P** |
| **设备列表** | **100 台** |
| **通道数** | 1 个（同账号同时发起远控的设备数） |
| **会话数** | 2 个（每台主控同时可开的远控标签页） |
| **分组数** | 3 个 |
| **文件传输** | 免费版普通文件服务器 |
| **隐私屏** | ✅ 有 |
| **网络** | 普通免费节点（非 RTC+VIP） |
| **风控** | 新账号 / 新设备 **24 小时内不可作为移动端被控** |

> 🎯 **本文最重要的一条发现**：
> **ToDesk 免费版不限时长，成本控制靠「4 Mbps 带宽上限 + 30 FPS」实现。**
> 这不是巧合 —— 这是**在免费版上做成本封顶的标准做法**：
> 时长不可控，但**码率是天然的成本闸门**（成本 ≈ 码率 × 时长，见成本测算表 §3）。
> ⇒ **我方免费版设计必须采用同一逻辑**：**不限时长、限码率/画质**，否则会在体验上直接被比下去（「你免费版还要限时？」）。

## 4. 商业模式路线差异（比功能表更重要）

| 模式 | 代表 | 用户付的到底是什么 | 对我方的启示 |
|---|---|---|---|
| **免费 + 增值订阅** | ToDesk、向日葵 | 画质 / 帧率 / 并发 / 设备数 | **我方主路线**；付费墙挂「画质 + 中继额度」 |
| **开源 + 自建服务端** | RustDesk | 自己出服务器；厂商卖托管/企业支持 | ⚠️ **最大威胁**：技术用户会拿它当「免费 + 无隐私顾虑」的替代；我方的**透明度卖点**在它面前会被稀释（它直接把服务端交给用户） |
| **商业订阅 + 个人免费** | TeamViewer | 商用授权 | 个人免费但**风控会断连**，体验口碑差；我方不复制 |

> **战略含义（重要）**：
> 我方差异点里「**连接模式指示 / 透明度**」（见 v2 §9，源自决策 D1）在**面向普通消费者**时成立；
> 但面对**技术型用户**，RustDesk 的「服务端你自己管」是**更强**的透明度。
> ⇒ 我方的透明度卖点**必须落在「无需自建也能看得见」**这个位置：
> 普通用户不想买服务器、不想配 NAT，
> 我们要给的是**「开箱即用 + 依然诚实告诉你流量走哪了」** —— 这才是竞品都没占的空位。

### 6.1 🔴 差异点一：「鸿蒙深度优化」必须重新定义

**核实结论**：向日葵**已有鸿蒙 NEXT 客户端**（`sunlogin.oray.com/download` → 鸿蒙NEXT 标签，版本 **V 1.6.0.1032198，2026.09**）。
但官方原文明确写着：

> 「支持发起手机和电脑远程桌面；**为了确保鸿蒙系统的兼容性和体验感，我们正在精细打磨细节，更多功能敬请期待**」

⇒ **竞品的鸿蒙版是「尝鲜版 / 仅控制端雏形」，不是完整能力。**

因此 v2 §9 中「鸿蒙深度优化 = ✅ 差异点」的写法**过于笼统、有被反驳的风险**（用户会截图说「向日葵有鸿蒙版」）。改为三层表述：

| 层级 | 内容 | 是否差异点 |
|---|---|---|
| L1 鸿蒙**控制端**存在 | 对手已有尝鲜版 | ❌ **不是差异点** |
| L2 鸿蒙**被控/完整能力**（输入法一致性、软键盘不遮挡、模拟触屏/鼠标双模式、多窗口） | 对手「敬请期待」 | ✅ **是差异点** |
| L3 鸿蒙**平板 + 眼镜桥接**组合场景 | 无人做 | ✅ **是差异点** |

**对外文案必须限定在 L2/L3**，禁止再写「鸿蒙专项优化是我们的独特优势」这种无定语句子。

### 6.2 差异点二：智能眼镜接入 —— 唯一「全员空缺」项

向日葵 / ToDesk / AnyDesk / RustDesk / TeamViewer **全部无眼镜相关能力**。
✅ 这是**唯一没有被验证过的真空位**，也是我方定位里最值得押注的一条。

**但必须同时承认风险（v2 §4 已定调）**：

| 风险 | 说明 |
|---|---|
| 硬件前提 | 眼镜需支持 DP Alt Mode（有线）或标准蓝牙 HID/A2DP；无此条件的眼镜**做不了** |
| 装机量 | 显示型眼镜（Xreal / Rokid 类）当前出货量远小于手机 ⇒ **P2 不能作为 P0 的存续理由** |
| 差异化可复制性 | 手机桥接路径对手 6–12 个月可跟进，**不是护城河**，是先发优势 |

⇒ 定位结论：**眼镜是「拉高品牌调性 + 抢媒体声量」的旗帜，不是「拉动留存」的引擎。**
真正拉动留存的必须是 §6.3 的**透明度**与 §6.4 的**移动被控能力**（后者是拉新钩子，见 §7）。

### 6.3 差异点三：连接模式指示 —— 成本最低、最不可被轻易反驳

对手**全部缺失**（RustDesk 部分开源实现可见状态，但对普通用户不可读）。
来源于决策 **D1**（中继明文可见 ⇒ 不宣称 E2E ⇒ 改为透明度卖点），**零额外成本**（客户端已有连接状态），却能形成可传播的品牌记忆点。

### 6.4 差异点四：手机作为被控端 —— 唯一「有真实付费意愿」的空位 `[新增]`

> ⚠️ **本节是对 §7 定位的修正**：v2 早期版本把「手机为核心终端 / 手机上真的好用」当作主护城河。
> 该论证**不成立** —— 控制端可以是 PC，长时会话主力也是 PC→PC。
> 真正拿得出手的差异点是 **「手机作为被控端」**。

**支撑证据**（均为级别 A，2026-09-14 抓取）

| 证据 | 出处 | 含义 |
|---|---|---|
| ToDesk 免费版：**「新账号 / 新设备 24 小时内不可作为移动端被控」** | ToDesk 价格页 | 移动被控被当作**风控 / 付费点**控制 |
| ToDesk 专业版仅「赠 **1 台**安卓被控」 | ToDesk 价格页 | 供给紧张，需**单独售卖** |
| **免 Root 控制安卓 = ¥25/月**（会员 ¥18） | ToDesk 价格页 | 有**真实付费意愿**，不是伪需求 |
| 向日葵：免 Root 控制**仅部分机型** | 官网 | 技术门槛真实存在 |

**为什么对手不给：** 技术难 + 成本高（免 Root 依赖无障碍 / MediaProjection，机型碎片化，需要逐机型适配）；
**为什么我们可以给：** 消费级最大的一块未被满足需求就在「帮爸妈调手机」——
这类用户**不会自建服务端**（RustDesk 在此无能为力），也**不愿意为了帮助爸妈而先买一个 ¥25/月 的插件**。

> 🔴 **风险声明**：
> ① 机型适配工作量容易被低估（建议先做白名单 + 可查机型列表）；
> ② 该能力容易与**远控诈骗**关联，安全设计必须比 PC 更严（见 v2 §3.6 安全底线）；
> ③ iOS 不能作被控端，宣传不得越过此边界。

> 🔴 **D8 补充（2026-09-14）："有付费意愿" ≠ "可以当主主张"**
> 本节四个证据证明的是「**对手在这里收费**」⇒ 它是**真空位、真差异化**；
> 但**频次 × 付费意愿撑不起一条订阅线**（一年几次、应急型）⇒ 仅过了**差异化测试**，没过**权重测试**。
> ⇒ 正确位置是 **获客钩子（拉新）**，**不是主主张**；主战场仍是 PC→PC 远程办公。完整论证见 v2 §9.3 的 D8 小节。

> 🔴 **D10 补充（2026-09-14）：「被控端能力」与「控制端是谁」无关**
> 本节全部证据针对的是**被控端能力**（免 Root 控制安卓）—— 它**不区分控制端是手机还是电脑**。
> 而**帮父母排障时子女更可能用电脑**（大屏看清对方在点哪里 + 键盘打字快 + 可边查边做）
> ⇒ **PC→手机 是钩子的主力路径**，已从「少见 / P2」提升到 **P0**（v2 §1 / §9.3）。⚠️ 仍属**获客钩子**，**不改 D8 的主主张结论**。
> ❓ **残留缺口**：**PC 作控制端时，竞品是否单独计费**（ToDesk 的 ¥25/月 插件是按「控制安卓」还是按「手机端」售卖，未取到证据）⇒ 见 **§9 #13**。

### 6.5 外接大屏 / 桌面模式适配核实结论 🔴 `[新增]`（2026-09-14 核实，原 §9 第 10 项）

**核实问题**：对手在 Samsung DeX / 华为 PC 模式 / Android 桌面模式下，给出的是**桌面化布局**，还是**被拉伸的手机界面**？
**这直接决定**：我方 v2 §2.3.2「外接大屏」是**可主张的差异点**，还是**及格线（对齐项）**。

**证据表**（级别 A = 厂商官方；B = 可复现的公开缺陷单；C = 社区用户个案）

| # | 来源 | 级别 | 结论 |
|---|---|---|---|
| 1 | **TeamViewer 官方社区**，资深版主回复，讨论 #67365「Can I remote into Samsung Dex?」（2019-07-17） | **A** | 官方原话：**「We support DeX on one side only. Connections from your DeX to any device using the Remote Control app is possible. The other way around is currently a feature request.」** ⇒ ① **控制端跑在 DeX 里**是支持的；② **被控端处于 DeX 会话** = **不支持**，官方列为 feature request |
| 2 | **RustDesk issue #14704「Cannot interact with remote Samsung DeX」**（2025-04-08 提交，已转 discussion #14707） | **B** | 被控机（S23 FE）**在 DeX 会话内**跑服务并共享整屏：**画面能出来，但客户端（Fire HD 8）完全无法注入触摸 / 键鼠**（"RustDesk doesn't pass through any input, even if A11y input is enabled"）；**换笔记本当控制端同样失败** |
| 3 | TeamViewer 社区 #29803「Android - Teamviewer Host Samsung Dex」 | C | Note8：**未接 DeX 底座时 Host 可用；接上底座后提示 "Remote Control is not Activated" 且激活失败** |
| 4 | TeamViewer 社区 #67365 跟帖（2020-02 / 2020-11） | C | 即便在 DeX 里当控制端也曾不可用：「you can't access lower part of the screen … mouse just stop moving」；控制光标「goes to phone touch screen instead of dex screen」 |
| 5 | ToDesk 移动端教程与问答（「ToDesk手机端如何开启横屏模式」·「ToDesk平板控制电脑如何设置全屏？」） | C | ToDesk 移动端是**手机 UI + 手动开横屏 / 手动设全屏**，**没有**「检测到外接显示 → 自动切换桌面化布局」的设计 ⇒ 与我方 §2.3.2 的触发条件**存在代差** |
| 6 | Samsung Knox 文档「Use Samsung DeX during a remote session」 | **A（但不属竞品）** | 三星**自家企业支持工具**里，控制端会得到 **desktop-like environment with mouse and keyboard support** ⇒ 该能力**原生存在**，但只出现在三星自己的企业工具中，**第三方远控均未提供** |

**结论**

1. 🔴 **没有一家第三方远控把「桌面模式适配」做成一等公民。** 现状只有两类形态：
   **(a) 跑得起来但 UI 仍是手机界面**（TeamViewer 控制端在 DeX —— 官方称支持，但历史缺陷显示不可用）；
   **(b) 干脆不支持**（**被控端处于 DeX 会话** —— TeamViewer 官方明确为 feature request；RustDesk 输入注入失败）。
2. ⇒ **我方 v2 §2.3.2「检测到外接显示 → 自动切换桌面化布局」是真空位**，**不是及格线**。本节据此把 §6 矩阵该行判为「**✅ 次级差异点**」。
3. 🔴 **但 D6 的裁决不变：空位 ≠ 可主张。** 外接大屏**仍不得对外作为主主张** —— 它依赖 ① 手机 USB-C 支持 DP Alt Mode（非全线）② 现场恰好有屏。空位只让它从「⚠️ 待定」升级为「**可对外说明的次级差异点**」，**不进首页主张**。
4. ⚠️ **窗口期约 1–2 年，之后会被追平**：Android 16 起大屏（>600dp）**取消应用限制屏幕方向与可调整尺寸的能力**（API 36 生效 / **API 37 取消豁免**）⇒ **对手也会被平台逼着适配**。与 §6.1 鸿蒙 L1 同理：**这是时间窗，不是护城河**。
5. 🔴 **意外收获（比第 2 条更硬）**：**「DeX 会话本身作为被控端」是全行业空白**（证据 1 的官方 feature request + 证据 2 的输入注入失败）。
   这条与 §6.4「手机作为被控端」**同源** —— 都卡在 **Android 输入注入（无障碍 / MediaProjection）与虚拟显示**上，
   ⇒ 反向印证 v2 §3.7 的判断：**「息屏串流 / 输入注入」属硬工程，不是对手 3–6 个月能补的短板。**
