## 11.6 第三轮：全屏 / 沉浸式（`[D22]`，2026-09-15 新增）

触发问题（原话）：「浏览器、PC、手机远程连接 PC，全屏时，可以实现沉浸式体验，这个 UI 设计有没有？」
**结论：没有。** 而且不是画漏了一张图，是**四处独立缺口**，根因只有一个：**这条需求从未被提出过**。

| # | 缺口 | 为什么是问题 |
|---|---|---|

## 11.8 第五轮：运营台认证与内部账号（`[D24]`，2026-09-15 新增）

**触发问题（用户原文）**：「**是否存在系统管理后台的登录，忘记密码，修改密码等的 UI 设计？**」

### 11.8.1 审计结论

| 问的 | 结论 | 证据 |
|---|---|---|
| 运营台**登录** | 🔴 **无稿** | 全稿无此帧；W5-04 ~ W5-06 **全部从「已登录 + 已带入角色」开始**（W5-04 chrome = 「运营台 · 客服视图」+ `.tag`「当前角色：客服」） |
| 后台**忘记密码** | 🔴 **无稿** | `docs/**/*.md` 搜 `后台登录 / 管理员登录 / 内部账号 / 员工账号 / 单点登录 / 双因素 / 运营账号 / 运营人员` = **0 命中**（「有 63 命中」是 `SSOT` 误配 `SSO`） |
| 后台**修改密码** | 🔴 **无稿** | 同上；C 端有 [W3-08](w3-账号与设备管理.html#w3-08)，运营台**没有任何对应帧** |
| 后台**开号 / 停用 / 离职回收** | 🔴 **无稿且无规格** | `账号与管理系统设计` §5.1 ~ §5.6 **一句都没写「这些人怎么证明自己是谁」** |
| C 端同类能力（对照） | ✅ 7/7 已有 | 登录注册 / 找回+恢复码 / 2FA / 设备 / 解绑 / 注销 / 改密（`[D23]`） |

> 🔴 **诊断（本轮的真正结论）**：这不是「缺一个登录页」的体验问题，而是 **`账号与管理系统设计` §5 整章建立在一个未声明的假设上**——
> 「登录的人已经在台里了」。⇒ §5.4 的 P0 硬项「**权限必须从第一天就分开**」**没有身份来源**（分角色 = 先有人），
> §5.5 审计里的「**谁**」**没有来源**（谁 = 哪个账号）。
> ⚠️ **与 `[D12-6]` 的关系必须说清**：`[D12-6]`「P0 不造后台」= 不做**完整后台**（定价版本 / 成本台账 / 报表 / 工单），
> <span class="no">不包含</span>**访问控制** —— 且 W5-04 / W5-05 / W5-06 本就已经是 P0 界面。
> 🔴 内页出了、入口没出 ⇒ 与 `[D23]`（「已登录态改密无处可去」）是**同一类结构缺口**。

### 11.8.2 三个被漏掉的风险（按严重度）

| # | 风险 | 说明 |
|---|---|---|
| 1 | 🔴 **全稿风险最高的入口，是唯一没有「门」的界面** | 运营台能查全网手机号 / 实名状态 / 每笔用量，还能**改额度、封禁、退款**；而 W5-04 ~ W5-06 三帧都假定「已经在里面」 |
| 2 | 🔴 **把 `[D12-6]` 读成「P0 不做认证」** | 这是本轮最危险的误读：认证是**访问控制**不是「后台功能」 |
| 3 | 🔴 **§5.4 的 P0 硬项与 §5.5 的审计「谁」都靠这帧才成立** | 没有身份来源 ⇒ 分角色是空文、审计缺主语 |

## 11.9 第六轮：在线支付链路（`[D25]`，2026-09-15 新增）

**触发问题（用户原文）**：「**是否有用户在线支付的UI设计？**」

### 11.9.1 审计结论

| 问的 | 结论 | 证据 |
|---|---|---|
| 商品 / 价格 / 选档位 | ✅ 有稿 | [W4-01](w4-计费与个人中心.html#w4-01) / [W4-02](w4-计费与个人中心.html#w4-02) |
| 选**支付方式** | ⚠️ **形同占位** | W4-01 只有两枚 `<span class="btn sm">微信支付 / 支付宝</span>`，无状态、无渠道差异、无失败分支 |
| **订单确认 / 结算页**（金额明细 · 优惠 · 发票抬头） | 🔴 **无稿** | W4-01 写了「是否有企业抬头可在支付前填写」，但**没有任何界面承载它** |
| **唤起第三方支付** | — | 🔴 **不属于我方界面**（收银台是第三方页面），**不出稿**；但要出「跳转前 / 跳转中」 |
| **支付结果页** | 🔴 **无稿** | 全稿无此帧；只有 W4-02 note 与 W4-04 note① 提到「支付成功后」的文案，**没有成帧** |
| 支付成功但**权益未到** | 🔴 **无稿** | 同上；这是**唯一会产生资金风险**的状态 |
| **自动续费扣款失败** | 🔴 **无稿** | [W4-08](w4-计费与个人中心.html#w4-08) 只画了「扣费前 5 日提醒」（成功路径）—— **只画了一半** |
| 账单 / 发票 / 退款 | ✅ 有稿 | [W4-06](w4-计费与个人中心.html#w4-06) |

> 🔴 **诊断（本轮的真正结论）**：全稿有「**购买页**」（下单**前**），**没有「支付本身」**。
> 支付是全流程**唯一「钱已经出去、权益还没到」**的状态 ⇒ 缺了它，用户唯一的求助路径是**找客服**。
> ⚠️ **边界**：微信 / 支付宝的**收银台页**、Apple 的**支付弹层**不是我方界面，**不需要出稿**；
> 但**跳转前（订单确认）· 跳转中（确认中）· 跳转后（结果）** 这三段**是我方界面**，必须出稿。
> ⚠️ **一处清单盲点**：商业化 §13.1 的四行分类全是「**状态告知型**」（执行体 / 可见化 / 常规商业化 / 不做），
> **没有「交易型界面」的归属** —— 而它恰好是**唯一会产生资金风险**的链路（已在 `[D25]` 中登记）。

### 11.9.2 五条为什么重要

| # | 理由 |
|---|---|
| 1 | 🔴 **「扣了钱没到账」是唯一会被截图发到社交平台的一类事故**，且**无法用话术补救** |
| 2 | **支付结果是全流程唯一的「不确定态出口」**（回调延迟 / 用户中途离开 / 网络中断） |
| 3 | **发票抬头必须支付前可填** —— W4-01 的承诺此前**无执行体** |
| 4 | **`[D14]` 的价格版本固化，在用户侧唯一可见位就是订单确认页**；否则版本管理只在后端成立 |
| 5 | **Web / 桌面端被 §10 定为「主购买入口」却全稿无此页** —— 这不是"有意不做"，是**双方都漏了** |

### ✅ 拍板：`[D25]` 在线支付链路

| 编号 | 决策 | 要点 | 归属文档 |
|---|---|---|---|
| **`[D25]`** | **支付链路四件一体**（订单确认 → 支付结果四态 → 扣款失败 → Web 购买页），**全 P0 / 全层①** | 🔴 **收银台（微信 / 支付宝）与 Apple 支付弹层在我方界面之外，不出稿**；🔴 **支付结果必须画全四态**（已开通 / 未完成 / **确认中** / 订单已关闭）；🔴 **「确认中」是「钱出去、权益没到」的唯一出口**；🔴 **不得猜测失败原因**（渠道不回传 ⇒ 只能写中性话术）；🔴 **不得自动重试扣款**；🔴 **失败 ≠ 终止**（先重试、再宽限，**不得静默降级**）；🔴 **订单必须固化下单当时的价格版本**；🔴 **支付结果页不得有任何推荐位**；🔴 **Web 购买页与 iOS 版（W4-02）是两套实现，不得合并** | `商业化与计费设计` **§13.8**（新增）/ §13.2 **#10–#13** · 新增 **`[D25]`** 块 · `账号与管理系统设计` **§4.6**（新增） |

> 🔴 **本轮唯一的「更严」条款**：**支付结果页严禁任何推荐位**（升级 / 加购 / 邀请好友）——
> 刚付完钱的一屏是**最容易被"顺手加一句"**的地方，与 §13.4 红线⑤（不做促销）同源。
